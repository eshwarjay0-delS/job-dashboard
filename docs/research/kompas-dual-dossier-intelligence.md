# Kompas dual-intelligence dossier — owner directive 29 October 2026

## Requested outcome

The owner wants one deep, source-grounded dossier combining NotebookLM-style multi-perspective teaching, natural two-speaker inquiry, accessible explanations, expert conceptual dissection and ChatGPT-style long-form interview dossiers. Inputs are a candidate resume, a job description, PDFs, prior chat conversations/transcribed PDFs and interview expectations. The final dossier must be technically deep enough for an engineer, intelligible to a beginner, and strategically credible for a director. Actual live spoken answers remain one candidate voice. Human realism means attributable operational constraints and decisions, not fabricated banter, colleagues, durations or percentages.

Source request: direct owner message 2026-10-29 in the ChatGPT Kompas conversation. The referenced ChatGPT chats and PDFs have not yet been supplied in this turn; do not claim their contents were merged.

## Source-grounded implementation

- Source module: src/lib/kompas-dossier-bots.ts.
- Authenticated route: POST /api/kompas/dossier/intelligence.
- Request mode: notebook, dossier, combined (default).
- Source types: resume, job_description, document, chat_transcript, interview_transcript, interview_expectations, candidate_correction.
- Resume AND JD required. Distinct source ids and per-source SHA-256 digests are retained. Request limit: 32 sources, 160K characters per source, 240K combined, rejection rather than truncation. Long source libraries need a future versioned, paginated persistent batch ingest; do not trim them silently.
- Independent Notebook Intelligence and ChatGPT-style Dossier Intelligence prompts receive the same original sources. Synthesis sees original sources as well as both drafts; reconciles rather than concatenates.
- Source records are JSON-serialized and treated as untrusted task data. ChatGPT session answers and synthetic dialogue are reference material, not independent proof of candidate experience. The JD is the role expectation, not a résumé fact.
- Runs through existing approved MFit LLM configuration (keysFor and callLLM), with no access to a person's ChatGPT subscription or consumer Gemini Notebook account. No user-provided provider key accepted in this route. Provider/model are returned per stage, and ledger records calls under kompas:dossier-*.
- Output is Markdown manuscripts with source ids, basic citation warnings and factualReview: required. Warning checks ids only, NOT semantic truth. No PDF generated by the endpoint yet.
- Authenticated account boundary, no-store response, per-account in-memory hourly limit, request-size checks. Rate limit is instance-local, not a durable cross-instance quota.

## Google Gemini Notebook (formerly NotebookLM) boundary

## The human-workbench realism contract

An answer can describe a busy manager, engineer constrained by downtime, a rollout disagreement and a later process improvement ONLY when the candidate actually supplied or confirmed that occurrence. Otherwise the scene goes in a separately labeled hypothetical practice dialogue. Depth emerges from technical constraints, operating evidence, reasoned choices and validation, not decorative office anecdotes. The same incident may be understood from analyst, engineer, architect, operations owner and director viewpoints, but facts must not morph.

A two-speaker discussion is a teaching instrument (curious/challenging voice and explanatory voice), NOT the format of a live answer. Kompas stays question-first, narrative where appropriate, technical when relevant. Full-career introductions draw on documented career, not a single tool.

## Master Bible, session mini dossiers and live latency (owner follow-up 29 October)

The owner clarified that each completed interview should produce its own mini dossier, and these should accumulate in a single, persistent master Bible for relevant reuse. Stop/temporary navigation is not an end; only explicit session End seals one record. Added server-side immutable mini storage plus compare-and-create revisions in src/lib/kompas-master-bible.ts, along with browser/desktop mini POST at src/app/api/kompas/dossier/mini/route.ts and the authenticated Supabase-manifest ingest. The page ends a session locally without waiting for network, posts its saved Q&A, and retries unsynced ended sessions after opening the dashboard. User's original browser transcript remains locally available. Minis are context/previous answers, not verified work events.

The master Bible's versioned hot inverted index is updated once per completed session. Each session's full Q&A mini remains in durable R2; the hot index compacts older text to a bounded number of chunks, so cold live lookup doesn't scan an entire lifetime of interviews. The manifest/dossier digest tracks source changes. A separate prepare step stores three-stage Notebook, dossier and unified Markdown manuscripts plus a source-index and active source-pair pointer. Live answer service retrieves both the active source-bound index and previously answered mini-session context, in parallel with an approximately 110ms optional per-retrieval wait ceiling; misses never block answer generation. Prior session content cannot be used as proof of a candidate's experience or metric; current resume and original supporting materials remain authoritative. Sources from prior chats/PDFs still need to be supplied to build the ultimate dossier.

Index lookup uses an inverted posting list, so query cost tracks matched posting lengths rather than multiplying total source-text length by query keywords. A deterministic 1,000-term lookup fixture and owner-isolation/concurrent-session tests were added; this is not a measured model latency claim. First-token performance still depends on network transport, request scheduling, provider queuing, model generation and guard checks. A 110ms retrieval budget is a cap on optional history reads, not an end-to-end latency SLA. Current serverless host can evict warm memory; R2 is durable source, not a guarantee of zero latency. Evaluate P50/P95/P99 actual first-visible-token and completion time before promising targets.

Known limits: in-memory last-four hot cache is per-instance; head pointer is best-effort across concurrent writes; the master hot index is bounded but each immutable mini is preserved. Text snippets are retrieved lexically; semantic paraphrases need subsequent measured reranking/embedding work. No user-level control panel for the new agents, no generated final PDF, no Gemini Notebook Enterprise license integration, and no authenticated end-to-end live model benchmark have yet been verified. Vercel preview and production status must be checked separately at the exact commit. New tests: scripts/tests/kompas-master-bible.test.mjs, scripts/tests/kompas-dual-dossier.test.mjs. CI/production delivery must not be recorded as verified until green at the PR head.
